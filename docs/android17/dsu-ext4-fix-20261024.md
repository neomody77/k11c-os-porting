# Android17：定位 virt APEX 的 EROFS 不兼容

## 已确认的启动阻塞

2026-10-24 使用独立、单次启动的 DSU 槽复测。将日志开关直接放到主 `init.rc` 的 `exec_start apexd-bootstrap` 前，并保留服务失败后进入 bootloader 的行为；观察器识别 fastboot 后执行普通 reboot，返回 Android16 后立即保存 pstore。原生 boot、super、vbmeta 和 userdata 分区均未刷写。

这次捕获到实际错误：

```text
apexd-bootstrap: Mounting failed for package /system/apex/com.android.virt.apex: No such device
apexd-bootstrap: Failed to activate apexes: Mounting failed for package /system/apex/com.android.virt.apex: No such device
reboot: Restarting system with command 'bootloader,bootstrap-apexd-failed'
```

原厂 5.10.157 内核配置为 `CONFIG_EXT4_FS=y`、`# CONFIG_EROFS_FS is not set`。逐个读取实际构建的 38 个 APEX（包括 CAPEX 内的原始 APEX）载荷魔数，37 个为 EXT4，只有 `com.android.virt.apex` 为 EROFS。Android16 同一模块的实际载荷为 EXT4。Android17 固定标签源码在 `packages/modules/Virtualization/build/apex/Android.bp` 为启用 AVF 的 virt APEX 显式指定了 EROFS，与本板原厂内核不兼容。

此前将 printk 开关放在独立的板级 `early-init` 动作中，执行顺序晚于主 init 中的 bootstrap 服务，无法覆盖这次早期失败。本轮把开关移到主动作内的服务启动前，并临时将 bootstrap 信息日志过滤为 WARNING 及以上。日志诊断改动不属于生产补丁；构建结束后恢复源码并卸载、删除临时 nsjail AppArmor 例外。

首个完整日志诊断镜像为 1,910,358,016 字节，SHA-256 为 `762750068929daf7f0d969508a29ee66d64a52741aeba8318e325741394b3560`。使用独立 4 GiB userdata；安装前后核对原有 DSU 槽元数据哈希和 backing 文件属性未改变。失败后约 65.74 秒确认 Android16 `SDK36`、`boot_completed=1`，pstore 已保存到私有工作区。该诊断槽随后已清理，保留原有 `android17` 和 `dsu` 槽。

## 修复与验收

新增 `0006-virt-apex-ext4-for-stock-kernel.patch`，将 virt APEX 的主机端载荷文件系统改为 EXT4，保留模块及其签名流程。`apex` 在该仓库中是符号链接，补丁必须作用于真实跟踪路径 `build/apex/Android.bp`。适配入口已加入第六个项目；真实固定标签 checkout 上首次应用和重复应用检查通过。

构建入口增加对最终 system 镜像内 `com.android.virt.apex` 的检查：提取其载荷头，要求 EXT4 魔数，避免未来再次产出原厂内核无法挂载的 virt APEX。该修复不表示 K11C 已获得 AVF 或受保护虚拟机功能验证。

修复后的诊断镜像为 1,936,052,224 字节，SHA-256 为 `9fe0ffc27b84f26bbf1e7a6ab1f1c421325a6a4465932b36f3d0bd3d55e91be4`；最终镜像提取出的 virt APEX 已验证为 EXT4。新增构建检查对原始 EROFS 镜像的拒绝测试、对修复镜像的接受测试均通过。

使用新建的独立 4 GiB userdata 单次启动，约 90.86 秒确认 SDK37、release17、`boot_completed=1`。板端 `gsi_tool status` 为 running，root 读取的 `ro.gsid.dsu_slot` 命中新试验槽，SELinux 为 Enforcing。已实际解锁并捕获桌面画面；system_server、zygote、SurfaceFlinger 正常运行，启动动画已退出，Mali-G52 OpenGL ES 3.2 渲染器和 1024×600 / 62 Hz 显示模式生效。

板级 RIL、蓝牙和 RTC helper 状态均为 active，传感器状态为 no-configured-device，符合本板配置；挂载后的 RIL 库哈希与 Android17 私有候选一致。自定义状态属性对普通 shell 不可读，必须从有读取权限的域检查，不能把空值误判为服务未执行。

最初 arm64 `CodecCapabilitiesTest` 实际运行 34 项，33 项通过；四项 AVC 溢出回归全部通过。当时唯一失败为已有 HEVC 帧率范围用例，其下限断言期望 0、实际为 1，后续处置见本节末链接。GPU-work 缺 map 用例因本轮 map 存在而跳过，不计为通过。崩溃缓冲区未见输出；这些检查仍不等于完整多媒体或外设兼容验证。

已构建去除全部临时日志/诊断策略改动的常规候选，保留本轮 DSU userdata、仅更新 system 后，约 37.72 秒再次完成 SDK37 启动。真实运行 arm/arm64 codec，各 33/34 通过，四项 AVC 回归均通过；GPU-work 缺 map 测试因 map 存在而跳过。20.10 秒亮屏、应用启动后短时样本 CPU 忙 6.33%，MemAvailable 3,002,024 KiB，SoC 55.555℃；这是导航补丁前的常规候选样本，不是完整流畅度或长期资源测试。

## 自然横屏三键导航

屏幕 1024×600、密度 200，使 Launcher 将本板归为 phone；但面板自然方向为横屏、显示旋转为 0。三键模式下，按钮布局、容器尺寸及窗口缩放三处代码按屏幕横竖方向选择侧边布局，而已有窗口创建逻辑按显示旋转将导航栏放在底部，导致按钮被裁剪在 60×60 小窗口。Android16 使用相同逻辑，切到三键后也能复现。

`0007-navbar-natural-landscape-rotation.patch` 将 `DimensionUtils.kt`、`NavButtonLayoutFactory.kt`、`TaskbarActivityContext.java` 的这三处判断统一到实际显示旋转。保持密度 200，不通过缩小 UI 或改成平板分类绕开问题。Android16 对应修复在其独立分支维护，并用同版本 Launcher 系统应用更新验证；原生 boot/super/vbmeta 未改写。

最终 Android17 常规 system 已集成 EXT4 和三键导航修复，无临时诊断策略，大小 1,936,048,128 字节，SHA-256 为 `bbdc2576aed08e910d0bfc58f0916dd0fe27714c6514a62c1f72df734f4f3669`。最终 system-only DSU 更新前后核对原有槽及本轮 userdata 属性，确认均保留；启动和三键结果见 [结构化实测](boot-results-20261024.json)。实际解锁后底栏为 1024×60，已通过真实屏幕点击验证返回、主页和最近任务卡片，保持 Enforcing。本次只实测旋转 0，其余旋转不宣称已在板上通过。

本阶段观察到的 HEVC 帧率断言与 Perfetto `vsock` 重启问题，已在同日后续验收中处理：保留正确生产计算、纠正过时 HEVC 断言后双架构各 34/34；Android17 去除不适用 VM relay 后本地 tracing 已跨镜像重启验证。详见 [后续记录](perfetto-hevc-20261024.md)。Android16 的 tracing 问题未在该后续阶段部署修复；完整外设、长期稳定及 CTS/VTS 未通过本次测试证明。

当前板子运行 Android17 单次 DSU，普通重启会回到原生 Android16。此前一次手动重启已由用户确认，不归因为 Android17 自发重启。旧 Android17 native super 仍含旧载荷，不可作为修复版使用，需重新打包和校验后再讨论原生安装；本轮未刷写原生固件分区。DSU backing 文件及明确执行的 Android16 Launcher 应用更新属于 userdata 文件系统写入。
