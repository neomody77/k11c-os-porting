# RIL 兼容候选与 AVC 能力复测

本轮在已验证的 Android16 GSI 上做可恢复的运行时实验，没有重装 DSU、清理 userdata 或写入 boot/vendor 分区。原始抓取和厂商二进制只在私有工作区保存。

## AVC 能力疑点关闭

旧 1080p60 样本平均码率 27,744,162 bps，厂商 AVC decoder 的声明范围为 1–20,000,000 bps。分别查询尺寸、尺寸加帧率、profile、level 都通过，加入码率后失败。旧样本完整能力查询 false 符合这个上限，不能据此断言能力声明错误。

新增有 VBV 限制的 Constrained Baseline Level4.2 样本：1920×1080、60fps、3秒，目标8Mbps、最大16Mbps、buffer16Mbps。最终自动选择复测的平均码率 9,347,464 bps；完整 isFormatSupported=true，MediaCodecList.findDecoderForFormat 自动选择 c2.rk.avc.decoder，180帧全部解完，EOS=true，解码1766ms。早一轮相同参数样本为9,328,077 bps，180帧/1788ms，同样通过。

旧高码率样本也仍解完180帧/1826ms，但它超过公开声明范围，不能据此提高上限。两类样本都保留，避免把压低测试负载误称为扩大硬件能力。本轮是 ByteBuffer 解码测试；之前的 Surface 测试结果不因此重写，不把解码吞吐当作屏幕FPS。

诊断增加逐项能力查询和自动选择断言。MediaFormat 的 frame-rate 可能是 Integer，读取时使用 getNumber，修复了新增诊断首次遇到的类型转换异常。Python runner 现在读取 probe JSON 的 PASS/FAIL；am instrument 退出0但 probe失败时不再记录成成功。

## RIL 的两层故障

1. Quectel 厂商库枚举 /apex 并选第一个 VNDK，误选31。vendor linker namespace仅允许33，dlopen失败后 property_get未初始化；RIL_Init调用空指针。
2. 在独立mount namespace仅保留可见VNDK33后，动态库初始化成功，但厂商版本表只认识最高Android14。实际release16对应160，返回RIL_VERSION=0，RIL_register拒绝后触发“joinRpcThreadpool without calling configureRpcThreadPool”中止。

仅在子进程隐藏旧VNDK、仅修改库路径都不足以修复第二层错误。独立LD_PRELOAD兼容探针同时纠正路径和RIL内部版本判断后，RIL PID保持不变超过30秒；它属于定位实验，未集成到GSI。直接从 /data/local/tmp preload被vendor namespace拒绝，实验随后使用子进程内的临时文件bind；原目录、图形库和全局namespace未改变。

## 精确厂商库候选

厂商RIL源码没有包含在当前AOSP中。因此先准备可复现的厂商库副本候选，保留源文件；它是有明确固件限制的兼容实验，不是从源码重编译的厂商RIL。

工具 [prepare-vendor-ril.py](../../tools/prepare-vendor-ril.py) 仅接受以下输入SHA256，并校验ARM64 ELF、原指令/字符串和完整输出SHA256。其它固件直接拒绝；既不写设备，也不覆盖已有输出目录。

| 文件 | SHA256 |
|---|---|
| 允许的原厂 librk-ril.so | 242fe86dfbdb5796674077ac55ffa4f6facc067c4b3e1bf519f0da5d2925ab5b |
| 候选副本 | f61f59dba68563eb9a037b6ac1c42bd3788724fdf9b94a52badc737624aeda8d |

改动限于四个区域共84字节：两个system绝对路径fallback改为SONAME；ql_find_libpath返回0，让原有vendor namespace解析匹配的VNDK库；版本判断仅对release160选择厂商已有RIL协议12，其它未支持版本仍返回0。没有修改实际Android版本属性、链接器规则或现有RIL函数表，也没有用停止RIL掩盖崩溃。Android17不在此候选支持范围内。

```bash
python3 tools/prepare-vendor-ril.py \
  --factory-library /path/to/private/librk-ril.so \
  --out /path/to/private/ril-candidate
```

输出包含厂商私有内容，不提交本仓库、不上传Release。原厂源码修复或支持新版本的厂商库仍是长期方案。

原init服务在radio用户和原capabilities下连续24次、每5秒采样均保持同一PID与running状态，观察120秒，IRadio1.0至1.5接口注册成功。日志确认Android Version160、RIL_VERSION12，进程maps中netutils/cutils均来自VNDK33。聚合数据见 [结果](ril-codec-results.json)。临时bind仅替换该服务打开的库文件；试验结束卸载bind并核对原库SHA256恢复，不能把运行时通过称为跨重启的持久修复。

第二次启动该服务后再次观察60秒、12次采样均为同PID/running；期间网络DNS/HTTPS200、Mali GPU300帧、自动选择硬件解码180帧均通过。两轮结束都恢复原库，未保留运行时覆盖。

下一阶段需集成到受控候选并验证冷启动、SELinux enforcing和原版回退。当前没有实体modem，未验证SIM、蜂窝数据、通话或radio错误恢复；注册HAL成功也不能替代这些验收。CTS/VTS和长期稳定性仍未完成。
